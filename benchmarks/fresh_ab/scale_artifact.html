The Grep Boundary

A code index was supposed to earn its keep on large repositories. Across a 26× corpus ladder it didn't. What it earned its keep on was questions that cross from one repository into another — where the grep-only agent went twelve for zero.

0 / 12
Cross-repo answers the grep-only arm got right

Given a question that could only be answered by comparing django, celery and sqlalchemy together, the grep-only agent produced zero correct answers in twelve attempts — 4 partial, 8 wrong — and confidently named a nonexistent or wrong symbol in 8 of those 12. The indexed arm scored 4 correct and 6 partial on the same questions.

Method

One hypothesis, built so it could fail.

Three new repositories were cloned and indexed for this run — celery (3,882 symbols), django (12,132) and sqlalchemy (13,175) — joining flask to form a ladder from 497 to 12,830 definitions. Twenty tickets were authored across three task shapes, every gold answer built by reading source code with no access to the index, then re-derived independently by a separate verifier.

Both arms received byte-identical prompts differing only in the tool list, and a hard budget of six tool calls that was deliberately not varied by repository size. Holding the budget constant is the instrument: if six calls suffice at 497 definitions but not at 12,830, the ladder reveals it. Judges saw only final answers, never traces — a trace from the indexed arm displays its own tool calls, so trace-level grading cannot be blinded.

Finding 01

Corpus size does not predict the advantage.

The result is non-monotonic, and the largest repository in the set is one where the index loses. Whatever drives the difference, raw corpus size is not it — which matters, because "adopt an index because your monorepo is big" is the standard industry pitch and this run does not support it.

Finding 02

Task shape predicts it, and one shape decides it.

The mechanism is not subtle. A cross-repo question requires holding three codebases side by side. Grep must be pointed at one tree at a time, and the agent then has to assemble and compare the results itself — under a six-call budget that the sweeping alone consumes. A single index search with no repository argument returns ranked hits across all three at once.

Adoption tells the same story from the agent's side: on cross-repo tickets the indexed arm used the index in 12 of 12 trials at a mean of 5.33 calls, more than double any other task shape. It reached for the index because nothing else could do the job.

Grep cannot see across repository boundaries, and an agent under a call budget cannot paper over that.

Finding 03

When a name has 39 implementations, grep declines to guess.

Disambiguation tickets ask which of several identically-named implementations actually runs in a described situation. Naming the bare function earns nothing; the judge scores a hit only if the answer identifies the specific sibling, with the right file and owning class.

The gap concentrates on the hardest case. Django's as_oracle has 39 definitions across 13 files: the indexed arm identified the right one 3 times out of 3, the grep-only arm once out of 3.

Note what the control arm did not do. It never named a wrong sibling. Its failure was declining to say which implementation at all — naming the function and stopping. That is the correct response to 39 indistinguishable hits: grep confirms the name exists 39 times and offers nothing to rank them by, so a careful agent refuses to guess. The index returns qualified names and owning classes, and the agent answers.

Finding 04

Both tools degrade as codebases grow — in opposite directions.

Two measurements taken during setup, before any benchmark agent ran. Together they explain why small-repo benchmarks kept coming back null, and they cut in both directions.

Why every earlier benchmark returned a null

The problem class this index exists to solve barely occurs in a small repository. Flask yields 2 ambiguity-hard blast-radius candidates and 1 disambiguation candidate; celery, django and sqlalchemy yield 10+ each. You cannot construct the hard case in a small codebase.

Three prior benchmarks all ran on repositories of 2,799 definitions or fewer. That is very likely why all three found no correctness effect.

Caveat

Read this before quoting any p-value here.

The headline is the least-powered cell in the run

Overall correctness is +0.117 at p = 0.11 — not significant across 20 tickets. No individual task class reaches p < 0.05 either.

The cross-repo result needs a caveat in both directions. The indexed arm wins 4 of 4 cross-repo tickets and the control arm scores zero correct out of twelve, which is a large effect. But with four paired tickets, a sign-flip permutation test cannot return a p below 0.125 no matter how big the effect is — the test is floor-limited by sample size.

So this finding is strong evidence and weak statistics at the same time. The right response is to power it properly with 12–15 cross-repo tickets, not to quote p = 0.12 as though it were a null.

Verdict

Not "your repo is big." "Your question crosses a boundary."

The case for installing a code index, as this run actually supports it:

  • Cross-repository questions. On questions spanning three services, the grep-only agent got zero right out of twelve. This is a capability difference, not an efficiency one.
  • Disambiguation at scale. When a name has dozens of implementations, grep returns dozens of indistinguishable hits and a careful agent declines to answer. The index resolves which one runs.
  • Not single-repo call-site enumeration. On what is probably the most common real task, grep-only wins — and it localized the target in 24 of 24 trials.
  • Not for speed. Seven seconds and five thousand tokens slower per task, both statistically significant, both replicated.

Limitations

  • One model tier (claude-haiku), 3 trials per ticket, and only 4 cross-repo tickets — the headline effect sits in the smallest cell.
  • A six-call budget may itself favour the arm needing fewer calls for cross-repo work. A budget sweep on cross-repo tickets alone would separate "better at this" from "better at this under a budget".
  • Two indexed-arm trials badly overran the budget (+14 and +10 calls). Violations are balanced overall at 5/60 versus 7/60, but the tail is not.
  • The corpus ladder is four repositories; per-repo scores rest on 4–5 tickets each.
  • Judges grade final answers only — deliberate, since trace-level grading cannot be blinded, but it means grading cannot see how an answer was reached.
